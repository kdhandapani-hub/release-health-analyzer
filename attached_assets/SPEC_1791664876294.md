# Release Health Analyzer — Specification

## 1. Problem Statement
After an infrastructure or application change (database patch, deployment, config change), engineering teams must answer one question quickly: **"Did this change break anything, where, and why?"**

Today that answer is scattered across four places:
- **API layer:** smoke/regression results live in one tool (e.g., Postman/Newman run reports).
- **Messaging layer:** event-stream health (Kafka consumer lag, throughput, errors) lives in another.
- **Database layer:** query performance and wait events (e.g., Oracle AWR-style history) live in a third, usually only visible to DBAs.
- **Infrastructure layer:** pod/node/host health (CPU, memory, restarts, I/O wait) lives in a fourth, usually owned by a platform team.

API failures and consumer lag are often *symptoms*. Infrastructure alerts are often symptoms too. The *root cause* is frequently a specific change, such as a SQL plan regression after a DB patch. Nobody sees all four layers on one timeline, so tracing symptom → cause, and ruling infrastructure in or out, is manual and slow.

**Goal:** A single interactive dashboard that combines API test results, event-stream metrics, database performance metrics, and infrastructure health, aligns them by time and change event, and makes the causal chain visible: **change → DB degradation → API latency/failures → consumer lag**, while showing whether infrastructure was a cause or a symptom.

## 2. Target Users
| User | Primary question |
|---|---|
| SRE / Production Support | Is the platform healthy right now? Where is it degrading? |
| Release Manager | Did the latest change cause regressions vs. the previous baseline? |
| Architect / Tech Lead | What is the root cause, and which services/topics/queries are fragile? |
| DBA | Which SQL or wait events are hurting the application tier? |
| Platform Engineer | Is any pod, broker, or host under resource pressure, and is it the cause or a symptom? |

## 3. Datasets (synthetic only)
All data is generated by `data/generate_data.py`. **No real, proprietary, or employer data is used.**

Time window: 14 days, hourly granularity (infra: 15-minute granularity is optional). One timezone (UTC) across all files.

**Linking key:** the same service names are used across all layers: `service` in API data, the owning service in `consumer_group`, the service embedded in the DB connection user (`db_user`), and `component` in infra data. Each service connects to the DB with its own service account, split by caller type, following the convention `SVC_<SERVICE>_<API|CONSUMER>` (e.g., `SVC_PAYMENTS_API`, `SVC_PAYMENTS_CONSUMER`). The app derives `service` and `caller_type` from `db_user`, so it can tell whether DB load comes from the API path or the Kafka consumer path.

*Why connection user rather than Oracle `MODULE`:* `MODULE` is often unset or generic (e.g., "JDBC Thin Client") unless every app explicitly sets it, while per-service connection accounts are a reliable, commonly enforced convention.

### 3.6 Injected scenarios (must be visible in the app)
- **Baseline:** API pass rate ~97–99%, p95 latency ~200–400 ms; low stable consumer lag; stable SQL elapsed times and plans; infra CPU ~30–55%, memory ~50–70%, no restarts.
- **Root-cause incident (day 9):** a `db_patch` change event is applied. Shortly after, one payments SQL ID (executed by both `SVC_PAYMENTS_API` and `SVC_PAYMENTS_CONSUMER`) switches to a new `plan_hash_value`, its `avg_elapsed_ms` jumps 5–10x, and `top_wait_class` shifts to User I/O. Within the same window (~6–10 hours):
  - the `payments` API shows higher latency, timeouts, and 5xx failures;
  - the `payment-events` consumer group (which writes to the DB) shows a lag spike and higher error rate;
  - **infra (symptom, not cause):** the DB host (`db-host-1`) shows rising `io_wait_pct` *after* the plan change (full scans drive I/O); payments app pods show only a mild CPU rise from retries; no restarts or OOMs.
- **App release on the same day (`R2026.10.09`):** deployed a few hours *before* the DB patch with no degradation, so the user must distinguish the real cause from a coincidental change.
- **Infra red herring (day 5):** `kafka-broker-2` hits memory pressure and restarts once, causing a short lag blip on one or two topics with **no** API or DB impact. The user should see this as an isolated infra event, not a release regression.
- **Minor noise:** occasional isolated test failures unrelated to any change.

## 4. Functional Requirements

### 4.1 Global sidebar filters (apply to every view)
- Date range
- Service (multi-select; applies to API service, consumer group owner, DB user, and app-tier infra component)
- Caller type: API / Consumer (multi-select; DB view)
- Change event (multi-select)
- Topic (multi-select)
- DB instance (multi-select)
- Infra tier: app / kafka / db (multi-select; infra view)

Every view must update consistently. Empty results show a clear message, not an error.

### 4.2 Views (tabs)
1. **Overview** — KPI cards with units, grouped by layer:
   - API: pass rate (%), p95 latency (ms)
   - Messaging: max consumer lag (messages), avg error rate (%)
   - Database: avg SQL elapsed time (ms), top wait class, active sessions
   - Infrastructure: peak CPU (%), peak memory (%), total restarts, unhealthy pods/hosts

   Delta vs. the previous baseline where applicable. A health indicator (green/amber/red) per layer.
2. **API Test Results** — pass rate by service and endpoint, latency distribution (p50/p95/p99), failure reasons breakdown, release-over-release comparison.
3. **Event Stream Health** — lag heatmap (topic/partition × time), throughput trend, top lagging consumer groups, error rate by topic.
4. **Database Health** — DB time by connection user (API vs. consumer path), top SQL by elapsed time, elapsed-time trend per SQL ID, wait class breakdown over time, plan change detection (flag any SQL whose `plan_hash_value` changed and whose elapsed time regressed).
5. **Infrastructure Health** *(stretch)* — CPU / memory / I/O wait heatmap by component × time, grouped by tier; restart and OOM event timeline; table of pods/hosts currently or recently unhealthy.
6. **Root Cause Correlation** — a time-aligned, multi-lane view (DB elapsed time / API failure rate & latency / consumer lag / infra resource pressure) with change-event markers. Highlight windows where layers breach configurable thresholds, and show which layer degraded *first*. Infra events that occur without degradation in other layers are labeled as isolated.
7. **AI Insights** — a button that sends a *summarized* view of the current filtered metrics (not raw rows) to an LLM and returns a plain-English summary: what degraded, in what order, likely root cause, whether infrastructure was a cause or a symptom, and recommended next checks.

## 5. Non-Functional Requirements
- **Stack:** Python 3.11+, Streamlit, pandas, Plotly. LLM via an API key read from an environment variable / Replit Secrets.
- **Structure:** `data/` (generation + loading), `analysis/` (metrics, correlation, plan-change detection, infra health rules), `views/` (one module per tab), `app.py` (entry point).
- **Performance:** cache data loading (`st.cache_data`).
- **Resilience:** the app runs fully without an LLM key; the AI tab shows a friendly fallback message. If `infra_metrics.csv` is missing, the app still runs and hides the infra tab and lane.
- **Clarity:** every metric shows its unit; charts have titles and axis labels.
- **Security:** no secrets in the repo; no real data.

## 6. Out of Scope
- Authentication / user management
- Real data ingestion (Newman, Kafka JMX/Prometheus, Oracle AWR/ASH, Kubernetes metrics-server / node exporters)
- Alerting and notifications
- Cloud deployment (optional bonus only)

(These are covered under "Production Path" in the documentation.)

## 7. Acceptance Criteria
**Core**
- [ ] `python data/generate_data.py` produces all CSVs with the injected scenarios.
- [ ] `streamlit run app.py` launches with all tabs.
- [ ] All filters affect all tabs; empty filter combinations show a message.
- [ ] The Database Health tab flags the day-9 plan regression.
- [ ] The Root Cause Correlation tab shows the DB degrading first, then API, then Kafka.
- [ ] The coincidental app release is visibly distinct from the real root cause.
- [ ] The AI Insights tab identifies the DB plan regression as the likely root cause, and degrades gracefully without a key.
- [ ] README includes setup, run steps, and screenshots.

**Stretch (infrastructure layer)**
- [ ] The Infrastructure Health tab shows the day-9 DB host I/O wait rising *after* the plan change (symptom, not cause).
- [ ] The day-5 Kafka broker restart appears as an isolated infra event with no API/DB impact.
- [ ] The AI summary correctly classifies infra as a symptom on day 9 and an isolated event on day 5.

## 8. Build Approach (vibe coding)
Built iteratively with an AI coding assistant (Replit Agent). Each step: prompt → run → verify against this spec → screenshot → log any bug and the corrective prompt in `PROMPTS.md`.

Suggested order: data generator → Overview → API tab → Kafka tab → DB tab → Correlation tab → edge cases & refactor → AI Insights → **(stretch)** infra data + Infrastructure tab + infra lane in Correlation.

**Cut line:** if time runs short, skip the stretch layer and list it under "Production Path." The core story is complete without it.
